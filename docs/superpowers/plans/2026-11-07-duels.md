# Duels ("דו-קרב") Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Live 1v1 math duels between friends (15 questions, 5 minutes, server-checked), with a friends system, behind an admin on/off/test switch.

**Architecture:** Postgres (Supabase "mathix") owns all state and rules through `security definer` functions that check our own session token; a Supabase Edge Function generates each duel's 15 questions from ported copies of Sulaiman's generators and writes them with hidden answers; Supabase Realtime broadcast (public channels with secret names) pushes "something changed" hints, and the client always re-reads the truth from `duel_state`. Next.js pages under `/duel` render the experience from the approved mockup.

**Tech Stack:** Next.js 16 / React 19 (JS/JSX like the rest of `src/`), Supabase Postgres 17 + pgTAP (`supabase test db`), Supabase Edge Functions (Deno), `@supabase/realtime-js`, `qrcode-generator`, Node's built-in test runner (`node --test`) for the question generators.

**Spec:** `docs/superpowers/specs/2026-11-07-duels-design.md` (+ `2026-11-07-duels-topic-audit.md`, mockup `design/duel/mockup.html`). Read all three before any task.

## Spike results

Task 0, 2026-11-08 (Supabase CLI 2.90.0, local edge runtime 1.73.3 / Deno 2.1.4). Client = `@supabase/realtime-js` 2.x (Node 22 WebSocket) with the publishable key from `src/lib/config.js`, channel `{private:false}`.

| Check | Local | Hosted (mathix) |
|---|---|---|
| `realtime.send(payload, 'hint', topic, false)` from SQL reaches a subscribed client | OK | **Not verified** — no DB access (see below) |
| Public channel subscribe + receive with publishable key | OK | OK (sent via `POST /realtime/v1/api/broadcast` with the publishable key → 202, client received it). So public access is on. |
| Edge function (`--no-verify-jwt`) called with only `apikey: sb_publishable_…` | OK (200) | **Not verified** — deploy refused (see below) |
| Write to DB from inside the function | OK | Not verified |
| Edge function → `SUPABASE_DB_URL` → `select realtime.send(...)` → client receives | OK | Not verified |

- **Env vars inside a local function:** `SUPABASE_URL` (internal `http://kong:8000`), `SUPABASE_ANON_KEY` (legacy JWT), `SUPABASE_SERVICE_ROLE_KEY` (legacy JWT), `SUPABASE_DB_URL`, `SUPABASE_JWKS`. **No `SUPABASE_SECRET_KEYS` / `SUPABASE_PUBLISHABLE_KEYS` locally.**
- **Writes worked with both** `SUPABASE_SERVICE_ROLE_KEY` (PostgREST insert with `apikey` + `Authorization: Bearer`, 201) and `SUPABASE_DB_URL` (`npm:postgres@3.4.5`, `prepare:false`, connects as `postgres`). **Recommendation: use `SUPABASE_DB_URL`** — it can also call `realtime.send` and security-definer functions directly, and it doesn't depend on the legacy-vs-new key naming (hosted projects may expose the new keys as `SUPABASE_SECRET_KEYS` JSON instead). Verify on hosted in the first task that deploys a function.
- **Surprises:**
  - Every broadcast sent by `realtime.send` arrives with an extra `id` field injected into `payload` (and `meta.id`). Clients must ignore unknown payload keys.
  - Locally, `--no-verify-jwt` functions answer even with **no** `apikey` header (200). Don't rely on the gateway for auth — the function must check our own session token.
  - **Hosted blocked:** the Supabase CLI on this Mac is logged in to a different account (org "markocity.admin@gmail.com's Org", project marko-city). Every mathix Management-API call returns 403 ("account does not have the necessary privileges"): `supabase functions deploy`, `supabase db query --linked`, and even `supabase migration list --linked`. So `supabase db push` and function deploys for mathix also need Abed to `supabase login` with the mathix account first. Nothing was deployed or changed on the hosted project.
  - Enabling `[realtime]` and `[edge_runtime]` in `supabase/config.toml` is required for `supabase start` to run them locally (done).

## Global Constraints

- Never edit `src/topics/*/Topic.jsx`; `python3 tools/verify-logic.py` must print "math and text untouched" at every commit.
- Never put a secret key in the site. Only the publishable key + public VAPID key may appear in `src/`.
- Every new table: RLS on, no anon table grants; access only via functions granted to `anon`. Every friend/duel function starts with `duel_guard(uid)` (switch `off` → `{error:'off'}`, `test` → only `accounts.duel_tester`, `on` → all).
- Errors are returned as `{error:'<code>'}` and mapped to Hebrew in `src/duel/api.js` (pattern of `src/lib/account.js`).
- Realtime payloads carry ids/counters only — never names, text, or answers. Client treats every event as a hint and re-fetches.
- Numbers from the spec: 15 questions · 300 s · invite lives 60 s · 30 s send cooldown · 40 invites/day · 20 friend requests/day · 100 friends max · start = questions written + 4 s · ends 300 s later (+2 s grace) · wrong → 2 s lock · score `round((100 + max(0, round(50 − 4·s))) × mult × (q15 ? 2 : 1))`, mult 1.2 at streak 3–4, 1.5 at 5+ · XP win 30 / draw 20 / loss 10, first 5 duels per day only · online = `online_at` within 70 s · ping every 20 s while visible · questions-ready timeout 10 s.
- Friend code alphabet `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`, length 6. Add friends by code only (no username search).
- Emote ids: `gg` (משחק טוב), `wow` (וואו!), `again` (עוד אחד?). Report reasons: `name`, `spam`, `other`. Subjects: `random`, `num`, `alg`, `fn`, `geo` (world keys from `src/home/worlds.js`).
- UI: Rubik, Hebrew never letter-spaced, phone-first (375 px), `prefers-reduced-motion` → no shake/confetti, instant bars. Effects only at: start, overtake, last question, last 30 s, result.
- Anything started for testing (`supabase start`, dev servers, browsers) is stopped at the end of the task.

## Review Focus

1. **Refresh / come back mid-duel** → screen resumes at the right question with the right remaining time (from server `now`, not the phone clock). Test in Task 8 (`resume after reload`) and Task 4 (`duel_state` returns my next idx).
2. **Phone clock wrong by minutes** → timer and 3-2-1 still match the opponent. Test in Task 6 (`clockOffset`).
3. **Double tap** on an answer or on "send challenge" → counted once. Tests in Task 3 (duplicate `duel_answer` same idx → `order` error, score unchanged) and Task 3 (two invites inside 30 s → `cooldown`).
4. **Race: accept at the same moment as cancel/expiry** → exactly one outcome; both screens agree. Test in Task 3 (`answer_invite` after `cancel`/expiry → `gone`).
5. **Opponent vanishes after accepting / question generation fails** → duel still ends (at `ends_at`, or `failed` after 10 s without questions) and nobody is stuck on a spinner. Tests in Task 3 (`finish_if_due` after ends_at; `failed` after 10 s) and Task 8 (UI shows the end state).
